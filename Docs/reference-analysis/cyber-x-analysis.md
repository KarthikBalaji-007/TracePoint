# Reference Analysis: cyber-x

Repository: `references/cyber-x`  
Assessment basis: checked-in source, SQLite schema/database, sample data, and README. This is a static code review; runtime behavior was not exercised.

## 1. Overall Architecture

Single Flask application serves static HTML/CSS/vanilla-JS pages and JSON API routes, backed by SQLite. Backend modules cover authentication, complaint/officer routes, hand-coded risk prediction, hotspot aggregation, similarity matching, and security utilities. The UI has separate citizen and officer screens. The README describes ML and “real-time” alerts, but source inspection shows the displayed prediction paths are mainly static seeded rows and deterministic rules; no transaction-stream processor is present.

## 2. Backend Technology and Structure

Python 3.10+, Flask 3, Flask-CORS, Werkzeug, SQLite, and optional pandas/NumPy/scikit-learn; Gemini package/API key is optional. `backend/app.py` creates the Flask app, registers `backend/routes.py`, and serves frontend files. `backend/database/db.py` wraps SQLite access; `schema.sql` defines users, stations, complaints, predictions, and alerts; `sample_data.py` seeds the demo. `prediction.py`, `hotspot.py`, and `similarity.py` hold analytics. `run_project.py` initializes the DB and launches Flask on localhost.

## 3. Frontend Technology and Structure

Semantic HTML, CSS, and vanilla ES6 JavaScript; Leaflet maps and Chart.js dashboards. Page files live under `frontend/`; `frontend/js/api.js` wraps calls, while `officer.js`, `officer_dashboard.js`, `prediction.js`, `hotspot.js`, `map.js`, `citizen.js`, and `similarity.js` implement the workflows. It is not a React/Vue SPA; pages share server endpoints and are navigated as individual documents.

## 4. Data Pipeline

At startup `run_project.py` initializes the database. `schema.sql` creates tables and `sample_data.py` populates synthetic citizens/officers, stations, complaints, activity records, predictions, and alerts. Citizen submissions and officer status/actions write to SQLite through routes. Risk prediction routes read stored `risk_predictions`, while hotspot and similarity endpoints query historical complaints. No scheduled ingestion, ETL, validated external source connector, model training job, or outcome-label update pipeline is implemented.

## 5. ML/Prediction Methodology

`backend/prediction.py` contains `train_withdrawal_risk_model`, which can fit a small RandomForestRegressor on latitude, longitude, and amount when enough rows and sklearn are available; its target is directly manufactured from amount (`amount / 2000 + 40`, clipped). This is not a cash-out outcome label. The main `calculate_area_risk` path instead calculates a fixed score from count bands, dominant crime category, average loss, and an unconditional +10 “recent 7-day pattern” statement. `get_all_predictions()` returns the pre-seeded prediction table. Therefore the operational dashboard predictions are not demonstrably generated by the regressor or by a temporally evaluated model.

## 6. Features Used for Prediction

The unused/auxiliary Random Forest takes latitude, longitude, and amount and predicts the synthetic amount-derived target. The active area heuristic uses area-name substring selection, number of cases, dominant crime type, average loss, and a fixed trend increment. Hotspot summaries use complaint location text, crime type, amount, coordinates, and total cases. Similarity uses crime type, location-text overlap, Haversine distance, and amount ratio. Incident time is stored but does not materially drive the main area score; there is no transaction sequence/velocity feature model.

## 7. Spatial/GIS Implementation

Complaints and police stations store latitude/longitude. Leaflet maps render complaint, ATM, and station markers; the security module supplies Haversine distance. `hotspot.py` groups cases by hard-coded location-name substring rules, then averages coordinates per group. Officer map search uses Nominatim geocoding, distance calculations, fixed 800m buffers and 5km incident searches; nearest police station routing is straight-line distance. This is useful visualization and approximate proximity logic, not learned spatial clustering or road routing. Google/Esri/OSM tile and Nominatim services are external dependencies.

## 8. Temporal/Event-Processing Implementation

Complaint date/time and created timestamps are stored in SQLite; analytics can group or display them. There is no event bus, streaming consumer, rolling time-window feature computation, event-time ordering, or online forecast update in the inspected prediction code. “Recent 7-day” text in `calculate_area_risk` is not derived from an explicit seven-day query in that scoring block, and hotspot trend strings are fixed by case-count bucket.

## 9. Risk-Scoring Methodology

Area risk starts at 30, adds 25/15 for case-count bands, 20/10 for dominant crime type, up to 15 for average loss, then always adds 10 for a claimed recent trend; result is clipped to 5–95 and mapped to categorical bands. Hotspot risk is another rule: counts >=18 yield `min(96, 76 + total_cases//2)`, >=10 yield `58 + 2*cases`, otherwise `35 + 3*cases`. Complaint list risk has amount/category rules. These are distinct hand-authored scores and not calibrated probabilities. Stored demo predictions include manually supplied risk values/reasons.

## 10. Real-Time Functionality

The Flask API supports synchronous complaint submission and updates. It can return alerts, activities, and dashboard stats from SQLite, but no SSE/WebSocket/broker, live bank feed, automatic external account freeze, or continuously updated prediction process was found. The README’s actionable alert language exceeds what a stored alert table and synchronous API alone establish. Optional Gemini assistant calls, if configured, are separate from the cash-out prediction engine.

## 11. Dashboard/Investigator Workflow

Citizen screens support registration/login, complaint submission, own complaints, safety guidance, and map views. Officer screens provide login, complaint queue/filter/status work, dashboard KPIs, predictions, hotspot map/analytics, similar-incident lookup, activity history, and alerts. SQLite persists complaint status and officer activities. This gives a broader case-workflow prototype than a pure risk dashboard, but does not establish dispatch integration, bank intervention acknowledgement, or case outcome feedback into a prediction model.

## 12. Data Sources

Primary source is local SQLite populated by `backend/database/sample_data.py`; citizens can submit records through the app. Static police-station and demo records are bundled. Geocoding/map tiles are external services (Nominatim, Google tile URLs, Esri, Leaflet resources); Gemini may be used by the assistant when configured. There is no demonstrated direct NCRP, UPI, bank, ATM-switch, or police CAD integration.

## 13. Synthetic/Simulated Components

Sample accounts, credentials, complaints, locations, amounts, officer activities, predictions, and alerts are demo content. The seed uses generated jitter and fixed/randomized amounts. Forecast rows and explanations are hand-authored in `sample_data.py`; area/hotspot scores and risk labels are deterministic rules; the optional regressor’s target is derived from amount. Do not interpret these as real data or trained cash-out ground truth.

## 15. Strengths

- End-to-end citizen complaint and officer case-management paths are represented.
- Relational schema links citizens, complaints, stations, officers, and alerts.
- Similar-incident matching exposes understandable component weights and uses geographic distance.
- Hotspot maps, officer queues, status updates, and activity records support an understandable investigator workflow.
- PII masking/security helpers and password hashing are present as concepts (deployment configuration still needs review).
- Degrades gracefully to an algorithmic risk path when optional ML dependencies are missing.

## 16. Weaknesses

- Main forecasts are seeded or heuristic; auxiliary regressor target is formulaically derived from amount and does not represent observed cash-out.
- “Recent trend” and hotspot trend narratives are not grounded in explicit temporal comparison in the scoring logic.
- String-based location grouping is brittle and hard-coded to a small set of place names; fallback grouping can mix jurisdictions.
- City centroid averaging loses point-level patterns, and Haversine lines are not travel routes.
- Alerts are database records, not evidence of real-time dispatch or bank action.
- Flask app contains broad route/static-serving responsibilities; SQLite and no migration/worker architecture constrain scale.
- Sensitive complaint descriptions/evidence and static demo credentials require rigorous production security, authorization, retention, and audit controls.
- External geocoding and tile providers introduce availability, policy, privacy, and key/configuration dependencies.

## 17. What Is Useful for TracePoint

- Model the complaint, jurisdiction, officer, alert, and station relationships explicitly where case operations require them.
- Keep case status/activity history connected to risk assessments so investigators can see what happened after an alert.
- Use transparent similar-incident retrieval as a separate evidence aid, with distance and component matches visible.
- Use the GIS interface for investigation and patrol context, while keeping prediction scores and measured facts distinct.
- Design citizen/investigator workflows around persistent records and clear ownership, but add authorization and audit semantics before sensitive use.

## 18. What Should Not Be Adopted

- Do not call an amount-derived regression target a cash-out forecast or use seeded prediction rows as model output.
- Do not label fixed count buckets as a seven-day trend without an actual time-window query and comparison baseline.
- Do not use substring place names as the production spatial index or treat averaged coordinates as a detected cluster.
- Do not describe static alerts as real-time financial intervention or automated bank freezing.
- Do not place demo credentials, weak fallback secrets, or sensitive complaint/evidence flows into production without security hardening.
- Do not merge all hand-authored rules into a single opaque risk number; preserve provenance, feature values, and score method.
